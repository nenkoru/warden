# Warden

*Русский перевод. Основной текст — [README.md](README.md) (English).*

**Warden — маленький агент, который всегда на посту.** Он привязан к одному **домену**: проекту, маку,
namespace в Kubernetes, серверу — чему угодно, что можно описать манифестом. Warden следит за доменом, сам чинит мелочи
в жёстких рамках и зовёт человека только тогда, когда это действительно нужно. Работа к этому моменту уже подготовлена:
ветка с зелёными тестами, файл с предложением, готовый diff. Человеку остаётся одна команда: `warden approve ID`.

Warden — один Go-бинарник. Он не зависит ни от одного харнесса, ни от сети, ни от чата. Модель нужна ему только для
решений, требующих суждения, и без неё цикл тоже работает.

## Near the loop

Агент «в цикле» ждёт одобрения на каждом шаге, агент «вне цикла» не спрашивает никогда. Warden работает **рядом с
циклом**:

- **сам** — обратимое и разрешённое: правило, выученное доверие (3 одобрения подряд), дневной лимит;
- **спрашивает** — всё, что упирается в floor (`always_ask`), в отклонение в прошлом или в отсутствие правила.
  Вопрос всегда приходит с подготовленной работой и одной строкой ответа: `warden approve ID` / `warden decline ID`;
- **только сообщает** — то, на что нет гранта (`grant = "k8s.apply"`) или что помечено `dry_run_only`;
- **молчит** — тихий тик пишет `latest.md`, и больше ничего. Пинг (Report/Ask hook) бывает только при новом.
- **реже дёргает, если ты не отвечаешь** — после двух пингов без твоей реакции (любая команда `status`, `report`,
  `approve`, `feedback`, `signal`, то же через `warden mcp`, или сигнал от тебя) следующий ждёт интервал тика, потом
  вдвое дольше и так до `backoff.max` (по умолчанию 7 дней). Новое не теряется: отчёт пишется, находки остаются
  «новыми» и уходят со следующим пингом. Критичное идёт сразу. Настройка: `backoff = { after = 2, max = "168h" }`
  (`after = -1` — выключить). `warden status` показывает состояние.

Триаж («стоит ли это внимания») — единственное, что Warden улучшает в себе сам. Учится он на твоих метках
(`warden feedback ID noise|digest|important`), а каждое изменение проходит через гейт с вкомпилированными инвариантами:
high/critical уязвимость, нехватку места и падающий check скрыть нельзя, тяжёлый инцидент нельзя игнорировать. Откат —
`warden rollback`.

Те же метки оценивают **источники** сигналов и лент («маховик новостей»): каждая новость уникальна, поэтому правило
триажа по одной метке редко срабатывает на следующую, а оценка источника обобщает. Оценка — `(важно + ½·сводка + 1) /
(меток + 2)`; после трёх меток источник с оценкой ≤ 0.25 становится на ступень тише (report → digest → ignore) и
перестаёт тратить вызовы мозга (классификация, RCA), а с оценкой ≥ 0.75 — громче (digest → report). Уязвимости, место,
checks и всё critical не приглушаются. Находки из сигналов (инциденты, новости, сообщения) теперь тоже лежат в
`last.json`, их можно пометить. Оценки видны в `warden status`.

## Домены и паки

Домен описывается в `domain.toml`: что **наблюдать** (`observe`, `inventory`), что можно **менять** (`act`, у каждого
действия свои floors), как **проверять** (`check`), откуда **новости** (`feeds`: OSV, GitHub releases, RSS) и какие
**MCP-серверы и скиллы** ему нужны. Шаг — это `cmd` (argv с `{param}`), `mcp` + `tool` или `builtin`. Вывод
превращается в находки через `map` (JSON-пути, `where`, шаблоны, regex для текста) или через `interpret = true`, когда
сырой текст разбирает модель.

| пак | что делает |
|---|---|
| `go-project` | инвентарь из go.mod/requirements/package-lock, OSV, релизы, тесты как health. Фикс — `go-bump` в отдельном worktree на новой ветке, в песочнице, с PR-описанием. Если после бампа не собирается или красные тесты — мозг чинит в том же worktree. Никогда не push и не merge. |
| `node-project` | то же для npm: `npm-bump` — прямая зависимость через `npm install PKG@FIX`, транзитивная через `overrides`; `--ignore-scripts`, кэш Warden'а, egress только на registry.npmjs.org. |
| `linux-host` | Linux-сервер: диск, упавшие systemd-юниты (system и user), GPU (температура, ECC), здоровье сервиса хоста (`service_url`, по умолчанию модельный сервер :8000) с «тихими часами», когда он может стоять намеренно; dpkg-пакеты как инвентарь, Ubuntu security notices. Только чтение: фикс — файл с предложением. |
| `python-project` | то же для PyPI: `pip-bump` правит `==`-пин в requirements.txt (маркеры и extras сохраняются), ставит набор в свежий `.warden-venv` в worktree (egress только на PyPI), тесты в нём; venv не коммитится. |
| `k8s-namespace` | Warning-события и CrashLoopBackOff становятся инцидентами, образы попадают в инвентарь, фикс — файл с предложением. `kubectl apply` возможен только с грантом `k8s.apply` и всегда спрашивает. |
| `macos` | диск, кэши (чистятся только командой самого инструмента и только из списка владельца, с грантом `mac.clean`), батарея и термалы, Homebrew Cellar как инвентарь. Начинает в dry-run. |

`warden packs` покажет доступные паки. Свой пак — это папка с `domain.toml`, `skills/` и, при желании, `.mcp.json`.

## Быстрый старт

```bash
go install github.com/nenkoru/warden/cmd/warden@latest   # или: go build -o ~/bin/warden ./cmd/warden
warden init --pack go-project --dir ~/src/myproj --config ~/src/myproj.warden.toml   # пишет mode = "dry-run"
warden tick --config ~/src/myproj.warden.toml      # один проход; отчёт в .warden/reports/latest.md
warden status --config ~/src/myproj.warden.toml    # что ждёт решения
warden approve a_1b2c3d4e --config ~/src/myproj.warden.toml
warden units --config ~/src/myproj.warden.toml     # launchd/systemd: пишет юниты, загружаешь ты
```

Когда отчёты dry-run тебя устраивают, поставь `mode = "act"` и правила, например
`rules = [{ act = "go-bump", then = "auto" }]`.

Демо (все во временной папке, вывод сохранён в `examples/`):

- `scripts/demo-go-project.sh` — репозиторий с `golang.org/x/text v0.3.7`, настоящие OSV и Go proxy. Warden нашёл
  3 уязвимости, сделал ветку `warden/bump-golang.org-x-text-v0.41.0` (go get и tidy в sandbox-exec с egress только на
  proxy/sum.golang.org, build и тесты без сети), написал PR-описание и дёрнул Report hook. Второй тик прошёл тихо, checkout
  владельца не тронут.
- `scripts/demo-macos.sh` — настоящий мак, dry-run: 367 компонентов Homebrew, 8 находок (мало места: 16.5 GB при
  пороге 25 GB; 14.4 GB регенерируемых кэшей). Ничего не почищено: нет гранта `mac.clean`.
- `scripts/demo-npm-pypi.sh` — настоящие OSV, npm registry и PyPI, без модели: `minimist 1.2.5 → 1.2.6` (npm install
  в песочнице с egress только на registry.npmjs.org, `--ignore-scripts`) и `requests 2.31.0 → 2.33.0` (пин в
  requirements.txt, свежий venv в worktree, тесты в нём; venv не закоммичен). Обе ветки с зелёными тестами.
- `scripts/live-brain.sh` — **живой мозг** (тратит токены, запускать осознанно): Claude Code через ACP
  (`claude-agent-acp@0.89.1`), изолированный и в песочнице, с логином владельца по ссылке. См. «Проверено вживую».
- `scripts/demo-k8s.sh` — **фикстура**: `kubectl` здесь — скрипт с записанным JSON, к кластеру никто не подключается.
  Найдено 3 инцидента (BackOff ×2, FailedMount, CrashLoopBackOff), написано 3 предложения, 2 образа в инвентаре,
  `apply` — только сообщение (нужен грант `k8s.apply`). MCP-сервер kubernetes отказан: его нет в `warden.lock`.

## Проверено вживую (27.10.2026)

Claude Code через ACP, логин владельца, только Claude (так решил владелец; GLM/Z.ai вживую не прогонялся). Проект —
`example.com/relay` на `quic-go v0.50.0`; вывод в `examples/live-brain-*.txt`.

1. **Бамп ломает сборку.** OSV: у quic-go 4 уязвимости, фикс — v0.59.1, где `quic.Connection` стал `*quic.Conn`.
   `go get`/`tidy` в песочнице, сборка падает (`undefined: quic.Connection`), мозг в том же worktree правит две
   сигнатуры (запросил ровно 2 правки, обе внутри worktree, обе разрешены), проверки зелёные, коммит и PR-описание.
   Тем же тиком сами (без мозга) забамплены 4 транзитивные `golang.org/x/*`.
2. **Инцидент из потока логов.** `warden listen` на `tail -F app.log`; строка `panic: … nil pointer dereference in
   relay.Pipe …` → тик → RCA мозга по коду (одноразовый detached worktree HEAD; правки там выбрасываются): причина —
   `Serve` не выходит при ошибке dial и зовёт `Pipe` с nil; мозг сверил строки и честно заметил, что `Serve` в HEAD
   нет (лог синтетический) → вопрос владельцу «починить в ветке», RCA прямо рядом с `warden approve`.
3. **Задача владельца** (`warden signal "warden task …"`): мозг в worktree написал `Version()` и таблицу тестов,
   проверки зелёные, ветка `warden/task-…`, результат — пункт «Done» в отчёте.

Что живой прогон нашёл и что исправлено: ACP-мозг запускался без песочницы и с полной конфигурацией владельца
(теперь изолирован, см. «Интеграции»); если после бампа не собиралось, мозг не звали; задачи из инцидентов делили
одну ветку; результат задачи не попадал в отчёт; RCA не видел код и не показывался рядом с вопросом. Протухший
логин в Keychain — теперь понятная строка с подсказкой.

## Интеграции

- **MCP.** Домены берут инструменты у MCP-серверов (stdio или streamable HTTP), stdio-серверы запускаются в песочнице
  со своим allowlist хостов. Сам Warden тоже MCP-сервер: `warden mcp --config …` даёт инструменты `warden_status`,
  `warden_report`, `warden_pending`, `warden_approve`, `warden_signal` и ресурс `warden://report/latest`.
  Подключается в Claude Code, Codex, pi и любой другой MCP-клиент.
- **ACP и эндпоинты.** Мозг — любой ACP-агент (`brain = { acp = [...] }`: Claude Code, Gemini CLI, Codex, pi) или
  Anthropic/OpenAI-совместимый эндпоинт (Claude, GLM через Z.ai с `auth = "bearer"`, OpenRouter, локальная
  Ollama/vLLM) со своим tool loop. ACP-агент запускается как действие: в песочнице, писать может только свою папку
  и worktree, который ему дали, сеть — только хосты модели (`brain.net`). На запросы разрешений отвечают floors:
  чтение и правка внутри worktree (не `.git`) — да, остальное (shell, web) — нет. Claude Code (`isolate = "claude"`,
  по умолчанию, если в argv есть claude) получает свою папку конфигурации: ни твоих настроек, ни MCP-серверов,
  плагинов, хуков, CLAUDE.md и памяти; логин — твой, по ссылке (Keychain только на чтение) или из
  `CLAUDE_CODE_OAUTH_TOKEN` (`claude setup-token`, для работы без присмотра). Протухший логин — понятная строка в
  отчёте с подсказкой.
- **Разговор.** Не-команда от владельца или доверенного («привет») получает ответ с состоянием, а не тишину;
  незнакомцы ответа не получают. Поток с `chat = true` — чат, а не лог: проходит каждая строка, тик через ~2 с, а
  не 20 (вживую на Linux-сервере с локальной моделью: «привет» → ответ за 3,3 с, вместе с вызовом модели для
  классификации; `warden status` — за 2,3 с).
- **Тихие часы мозга.** `brain = { …, quiet = "0030-0800", tz = "Europe/Berlin" }`: в окне модель не зовётся вовсе
  (общий GPU ночью), находки идут как обычно, суждение ждёт.
- **Agent Skills.** `skills/` пака и скиллы из расширений попадают к мозгу как индекс, полный текст отдаёт `read_skill`.
  Кроме этого мозг получает инструменты read-only MCP-серверов домена (запущенных с `--read-only`) для RCA и предложений.
- **Hooks** в форме Claude Code: `Wake`, `Finding`, `PreAction` (может заблокировать: exit 2 или
  `{"decision":"block"}`), `PostAction`, `Ask`, `Report`, `Signal`. JSON идёт на stdin. Через них Warden дотягивается до
  Telegram, командного чата, трекера задач или почты — сам он сообщений не шлёт.
- **A2A.** `warden serve` отдаёт agent card и JSON-RPC на `/a2a`, плюс `POST /signal` и `GET /report`. Отправителя
  определяет bearer-токен, уровень доверия — списки `[serve] owners / trusted`.
- **Реестры.** `warden add mcp:…|skill:…|plugin:…@marketplace|pi:…` резолвит, скачивает, проверяет и пишет
  `warden.lock`; `warden verify` перепроверяет байты. MCP-сервер из реестра, которого нет в lock или который не прошёл
  проверку, Warden не запускает и пишет в отчёте, что делать (`run warden add …`). Хуки из плагинов выключены, пока
  их не включат по имени (`enable_hooks`).
- **Сигналы.** RSS/Atom (первый взгляд — baseline), команды, печатающие JSON-строки (адаптер к любому чату), папки,
  потоки (`journalctl -f`, `kubectl get events -w`) в режиме `warden listen`, webhook и A2A через `warden serve`,
  локальный `warden signal TEXT`. Что сигнал может вызвать, ограничивает уровень доверия: `update` и `task` от
  доверенного превращаются в вопрос владельцу, чужак получает строку в сводке и никакого ответа. Утверждения
  проверяются: advisory ищется в OSV и сверяется с настоящим инвентарём.

## Безопасность

- **Песочница закрыта по умолчанию.** `sandbox-exec` (macOS) или `bwrap` (Linux): запись только в рабочую папку, egress
  через собственный allowlist-прокси. Если раннера нет, Warden наблюдает и отчитывается, но отказывает во всём, что
  пишет или исполняет: действиях, sandboxed checks, stdio MCP, ACP-мозге, хуках, ответах. В отчёте строка:
  `no sandbox available: set sandbox = "none" to run unsandboxed — your choice`. Явное `sandbox = "none"` разрешено и
  видно в шапке каждого отчёта: `sandbox: NONE (owner's choice)`.
- **Ubuntu 24.04 и bwrap.** Установленного `bubblewrap` мало: AppArmor (`kernel.apparmor_restrict_unprivileged_userns
  = 1`) не даёт ему user namespace, и любой запуск падает с `setting up uid map: Permission denied`. Warden это
  проверяет и честно пишет «песочницы нет». Узкое решение — профиль только для bwrap (решение владельца, нужен sudo):
  `/etc/apparmor.d/bwrap` с телом `abi <abi/4.0>, include <tunables/global> profile bwrap /usr/bin/bwrap
  flags=(unconfined) { userns, }`, затем `sudo apparmor_parser -r /etc/apparmor.d/bwrap`.
- Floors проверяются кодом, а не моделью: `reversible`, `always_ask`, `grant`, `max_per_day`, `dry_run_only`,
  `where = "worktree"`, `sandbox` + `net`. Политика решает по порядку: deny-правила → floors → правила/закрепления →
  выученное → лимиты → dry-run.
- Новый домен стартует в dry-run. Ответы от твоего имени тоже dry-run, пока не задано `replies = true`. Warden не
  трогает твои конфиги агентов, не делает push и merge, не удаляет пользовательские данные.
- `tool-clean` запускает собственную clean-команду инструмента **вне песочницы — так задумано** (`go clean -cache`
  в песочнице «пиши только сюда» не работает). Защищают его грант `mac.clean`, список владельца `params.clean` и точное
  совпадение argv; без доступной песочницы он тоже отказывается.
- Устойчивость: `journal.jsonl` с begin/end, атомарная запись состояния, flock на тик, ключи идемпотентности, повтор
  после неудачи — не чаще раза в сутки. После краха следующий тик убирает брошенный worktree и пишет об этом.

## Ресурсы

Один бинарник (~15 MB) и три зависимости (go-toml, MCP go-sdk, acp-go-sdk). Между тиками в timer-режиме не работает
ничего, тики запускает launchd/systemd. В listen-режиме один процесс спит на чтении потоков. Состояние — файлы
в `.warden/` рядом с `warden.toml`.

## Ограничения v1

- `warden update` (самообновление по сигналу) не поддерживается: пересобери вручную.
- Источник сигналов `mcp` (опрос MCP-инструмента) не реализован; оберни его в `command`.
- ACP-мозг не получает инструменты Warden (MCP/read_skill/run_checks): он правит файлы своими инструментами, а
  проверки после него прогоняет Warden. Об этом ему говорится в задаче.
- ACP-агент читает своими инструментами без запроса разрешения; чтение ограничено песочницей (закрыты `~/.ssh`,
  `~/.aws`, `~/.gnupg`, Keychain кроме логина), а не worktree. Запись — только worktree и своя папка.
- Логин Claude Code по ссылке не обновляется изнутри песочницы (Keychain только на чтение): когда токен протухнет,
  запусти `claude` один раз или задай `CLAUDE_CODE_OAUTH_TOKEN`.
- `pip-bump` требует `==`-пинов в requirements.txt (poetry/uv lock не читаются); `npm-bump` — package-lock.json v2+.
- «Read-only» MCP-сервер определяется по аргументу `--read-only`.
- Реестры: per-platform optional-зависимости npm не пинятся (только заметка в lock), `uvx` резолвит транзитивные
  зависимости при запуске, inline hooks/mcpServers из `plugin.json` отмечаются, но не извлекаются.
- Мак-пак измеряет кэши через `du`, и это может занять секунды. Ненужные наблюдатели выключаются через
  `params.skip = "caches,library-caches"`.
